# SQLite 실행 계측 프로토타입

질문: 실제 SQLite를 실행하면서 "쿼리가 데이터를 행 단위로 어떻게 처리하는지"를
기록할 수 있는가? (실패하면 자체 교육용 SQL 엔진으로 간다)

## 방법

SQLite 3.54.0 원본의 실행 루프(`sqlite3VdbeExec`)에 훅 호출 한 줄을 넣는다.
훅은 opcode가 실행되기 직전에 불려서 opcode와 피연산자, 커서가 가리키는 행의
rowid, 직전 opcode가 레지스터에 쓴 값, 결과 행을 JSON 한 줄씩 남긴다.
브라우저 화면(`web/src/sql/`)이 이 기록을 "행 방문 → 값 읽기 → 비교 → 결과" 사건으로 묶는다.

```
./build.sh          # emsdk 6.0.10 → build/web/sqltrace.mjs·.wasm
cd ../../web && npm run engine    # 빌드 후 web/public/sql/로 복사
```

## 결과 (2026-10-15) — 성공

| 쿼리 | 실행 opcode | 기록으로 복원한 처리 과정 |
|---|---|---|
| `WHERE age > 30` | 28 | 5행을 차례로 방문, 행마다 age를 읽어 비교, 3행 출력·2행 탈락 |
| 같은 쿼리 + `age` 인덱스 | 20 | 인덱스에서 `age > 30` 위치로 바로 이동, 3행만 방문 (age 순서로) |
| `JOIN ... ON o.user_id = u.id` | 31 | orders를 순회하며 행마다 users를 rowid로 바로 찾아가는 중첩 루프 |
| `ORDER BY age` | 49 | 통과한 행을 정렬 버퍼에 넣고, 정렬 후 순서대로 꺼내 출력 |
| `GROUP BY user_id` + `SUM` | 118 | 정렬 → 그룹 키 비교 → 합계 누적 → 키가 바뀌면 그룹 결과 출력 |

인덱스 유무에 따라 실행 과정이 실제로 달라지는 것까지 그대로 드러난다.
바이트코드 기록에는 화면에 필요한 정보가 모두 있다. 남은 일은 계측이 아니라
변환층(바이트코드 → 학습자가 읽는 개념)이다.

## 알려진 한계 — 변환층에서 풀 것

- 정렬 버퍼·의사 커서(OpenPseudo)의 열 이름이 없다 → MakeRecord 레지스터 배치로 추론
- 정렬 버퍼에 넣거나 집계에 누적한 행도 "탈락"으로 표시된다 → SorterInsert·AggStep을 기여로 판정
- 그룹 경계(Compare/Jump)와 AggStep1(첫 실행 후 AggStep이 바뀐 이름)을 해설하지 못한다
- 비교는 "점프/통과"로만 나온다. `age > 30`이 `Le → 다음 행으로 점프`로 컴파일되므로,
  점프 대상이 루프의 Next면 "조건 불만족"으로 번역해야 한다
- 인덱스 항목의 키 값(예: age=34)은 아직 기록하지 않는다
- 서브쿼리·CTE·윈도 함수(코루틴, OP_Yield)는 시험하지 않았다
